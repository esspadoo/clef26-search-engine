\section{Methodology}
\label{sec:methodology}

Describe the methodology you have adopted, the architecture of your system, your workflow, etc.

We started by implementing a basic pipeline using BM25 as baseline, using Apache Lucene as the underlying framework.
We then experimented with different stop lists, filters and weightings to  improve the MRR@5 score, used as final score
in the CheckThat! Lab. We then proceeded to experiment with multi-stage pipelines based on neural models, which is the
final structure of our project.
\newline
We implemented a three-stage pipeline (figure \ref{fig:pipeline}) for our information retrieval system, consisting of:
\begin{itemize}
    \item \textbf{Query expansion}: We expanded the original query with additional context to bridge the gap between informal and scientific language.
    \item \textbf{Retrieval}: We retrieved relevant documents from the corpus using the expanded query.
    \item \textbf{Reranking}: We reranked the retrieved documents based on their relevance to the original query.
\end{itemize}
For each of these stages, we experimented with different models, chosing the ones that performed better in relation to the others.

\subsection{Query Expansion} \label{sub:queryexp}
The first step in our pipeline is query expansion: given the original query, we generate extra terms and tokens related to it.
This serves two purposes: to increase the number of available tokens for a match, and to bridge the gap between the original
informal query and the formal academic language used in the document corpus.\newline

augmentation. This model was prompted to generate three distinct representations for the given query,
tailored to our multi-stage retrieval needs:
\begin{itemize}
    \item \textit{sparse}: A list of domain-specific keywords and technical synonyms (e.g., scientific nomenclature)
    designed to maximize lexical overlap and mitigate the vocabulary mismatch in BM25-based retrieval.
    \item \textit{dense}: A semantically enriched re-phrasing of the claim that provides a broader context, allowing the
    bi-encoder in the next step of the architecture to produce more robust embeddings in the high-dimensional vector space.
    \item \textit{ColBERT}: A structured, formal version of the claim (e.g., "Serum levels and ICU admission") that provides coherent

\subsection{Retrieval} \label{sub:retrieval}
The retrieval stage is designed as a high-recall candidate generator between query expansion and neural reranking. Its objective is not to make the final relevance decision, but to ensure that the true source paper is included in a sufficiently large candidate set for the subsequent, more expensive cross-encoder stage. For this reason, after experimenting with a Lucene BM25 baseline, BGE-M3 only on dense vectors, the final pipeline uses the hybrid BGE-M3 retriever.\\ 
This choice reflects the nature of the task: social media claims often contain informal paraphrases, hashtags, named entities, numbers, and fragments of scientific terminology, so relying only on exact lexical overlap or only on dense semantic similarity would discard useful evidence.

The retriever searches the fixed paper collection provided by the task organizers and named\\ \texttt{collection\_data.json}.\\ Each paper is represented at document level by the concatenation of its title and abstract, and the retrieved unit is always the paper \texttt{pubkey}. We did not split papers into smaller chunks because the task requires identifying the source publication rather than retrieving an evidence passage, and using one representation per paper avoids an additional chunk-to-document aggregation step. Although the collection also contains metadata such as venue and authors, the hybrid retriever uses only title and abstract, which are the fields consistently encoded for all documents.

The expansion step provides three views of the same information need: an \texttt{embedding} view for semantic matching, a \texttt{sparse} view for lexical and terminology-based evidence, and a \texttt{colbert} view for fine-grained token interaction. BGE-M3 is well suited to this setting because it can produce dense vectors, sparse lexical weights, and ColBERT-style multi-vector representations from the same multilingual model \cite{bge-m3}. Thus, the retriever can combine broad semantic matching with exact term evidence and token-level matching without switching between unrelated encoders.

Candidate selection is performed in two steps. First, all documents are encoded as dense BGE-M3 vectors and searched with an inner-product FAISS index \citep{faiss_documentation}. This dense stage is used as an efficient broad filter over the whole collection. The default setting retrieves a large pool, \texttt{candidate\_multiplier} $\times$ \texttt{top\_k}, with \texttt{candidate\_multiplier=3} and \texttt{top\_k=1000}, before the final truncation. This deliberately large candidate set favours recall, which is more important at this stage than precision. Second, the dense candidates are rescored using the sparse and ColBERT representations. The sparse component rewards important overlapping terms, while the ColBERT-style component captures local token correspondences that may be lost in a single dense vector \citep{KhattabZaharia2020}.

The final configuration was selected through a sequence of runs recorded during development. We first tuned the lexical baseline by varying the Lucene analyzer, stop lists, stemming strategy, and BM25 searcher variants. These experiments improved the classical baseline but also showed its limitation for this task: even with query expansion and reranking, BM25-based candidate generation remained more dependent on surface overlap than desired. We then tested dense retrieval with BGE models, which improved the semantic coverage of the candidate set, especially for paraphrased or multilingual claims. The best retrieval-only results in the analysis came from the BGE-M3 hybrid variants, confirming the motivation for combining semantic, lexical, and token-interaction evidence in the same first-stage retriever.

Among the hybrid configurations, the run labelled \texttt{bge\_m3\_hybrid\_513} was retained because it gave the strongest recall-oriented trade-off among the tested no-rerank retrievers: it used weights $0.5/0.15/0.35$ for dense, sparse, and ColBERT scoring, respectively, with multiplier $3$ and maximum hybrid length $384$. A closely related configuration with a larger ColBERT weight obtained a nearly identical MRR@5 but lower Recall@100, so we preferred the setting that better matched the role of retrieval as a candidate generator. This choice was further confirmed by downstream runs: reranking the candidates from \texttt{bge\_m3\_hybrid\_513} consistently outperformed the corresponding BM25-based reranked runs, and increasing the reranked candidate depth from a few hundred documents to 500--1000 documents improved the final recall available to the reranker.

We also experimented with a learned fusion strategy for these hybrid signals. In particular, the experimental test performed includes a LightGBM LambdaMART option that builds features from the dense, sparse, and ColBERT scores, together with normalized score variants and dense-rank features, and then learns how to combine them. However, the retained retrieval configuration uses the simpler linear fusion, which was easier to reproduce and aligned well with the recall-oriented role of this stage. The score used in the final hybrid retriever is therefore:
\[
    s(q,d) = 0.5\,s_{\mathrm{dense}}(q,d) + 0.15\,s_{\mathrm{sparse}}(q,d) + 0.35\,s_{\mathrm{colbert}}(q,d).
\]

The largest weight is assigned to the dense score because it provides the main multilingual semantic signal; the sparse and ColBERT terms add complementary lexical and fine-grained matching evidence. Candidates are sorted by this score in descending order and truncated to the final \texttt{top\_k}. The retrieval output is a JSON mapping from query id to an ordered list of paper \texttt{pubkey}s, written by default to \texttt{results/bi\_encoder\_results.json}. Scores are not exported, because the next stage treats retrieval as a candidate generator and recomputes relevance with a cross-encoder over the returned document identifiers.
